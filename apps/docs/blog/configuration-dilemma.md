# 组件库靠配置活得很好。逻辑一配置，团队就开始写回函数。

**作者：** heyongqi10  
**类型：** Engineering Deep Dive  
**给谁看：** 做过低代码 / 逻辑引擎 / 「把业务也组件化」的前端与架构同学

---

视图能封装进组件库，传参加自定义能盖住大部分项目。逻辑也能做成函数库，ahooks、VueUse 都在证明这件事。

但现场用法完全不是一回事：组件库大家真会「选零件、填配置」；逻辑库里真正被复用的往往只有一两个 hooks，剩下的业务还是手写。

你也可以硬做「巨型 options + 插槽式自定义」，理论上能吞掉很多分支。大家就是不这么用。

这就是配置化的困境：同一套「参数化抽象」在视图侧是生产力，在逻辑侧经常变成没人愿意维护的第二套语言。

## 视图为什么适合配置化

视图的变化轴少，而且大体可枚举。

尺寸、状态、主题、布局变体、内容插槽。设计系统把高频形态收成有限 API，尾巴用 slot 或 style 覆写。调用方的心智是「选零件」，和设计稿同构。

所以 Element、Ant Design 这类库能活：问题空间近似「有限配置空间」。你愿意学一遍 API，因为它换来的是全项目一致的按钮、表单和无障碍行为。

配置在这里是压缩重复，不是假装业务不存在。

## 逻辑为什么扛不住同一套用法

逻辑的变化轴是业务语义，不是外观参数。

同样叫「请求」，后面可能叠鉴权、重试、竞态取消、缓存、错误码映射、埋点、灰度。组合是爆炸的，不是再加三个 prop 就能收敛的。

ahooks / VueUse 真正被广泛复用的，几乎都是**与业务无关的机制**：防抖、事件监听、媒体查询、局部状态同步。它们不是「下单」，也不是「结算」。

机制可以库化。业务叙事通常不能。

硬把业务叙事塞进「传参 + 自定义」，你会得到一个巨无的配置对象：读起来不像业务，改起来像改 YAML 小说，Code Review 时没人敢碰。团队的理性选择是退回函数，在 TypeScript 里把意图写清楚。

这不是工程师懒，是抽象选错了面。

## 我们差点用 JSON 重造了一遍 JavaScript

在 logic-render 里，我们做过声明式编排：`then` / `if` / `while` / `for` / `callFunc`，再加一批 `$add`、`$gt` 之类的表达式原子。文档还故意对齐 MDN 的指南结构，好让会 JS 的人快速迁移。

迁移是顺的。问题也跟着来了：

| JS | FlowSpec |
| --- | --- |
| 语句块 | `then.nodes` |
| `if` / `switch` / `try` | 同名节点 |
| `while` / `for` | 同名节点（外加 `maxIter`） |
| 函数调用 | `callFunc` |
| `a + b` | `{ "$add": [a, b] }` |

控制流骨架几乎一一对应。若目标只是「在 Node 里跑业务」，直接写 TypeScript 更短，调试器更好用，也不用学第二套语法。

对齐 JS 降低了学习成本，也暴露了配置化的极限：当你把「可配置」推到「完整语句与表达式」，你已经不是在做组件库式的零件拼装，你是在重造一门语言，只是载体换成了 JSON。

这门语言还更差写。中缀没了，类型提示弱了，堆栈信息绕了一层。唯一多出来的，是「程序变成了数据」。

## 「程序即数据」什么时候才值这个价

配置化逻辑不是永远错。它只在 JS 源码**给不了或不该给**的约束下才划算：

1. **要校验、要 diff、要给非运行时消费者看。** JSON 协议可以被 schema 拒绝，可以被 AI 或可视化编辑器生成，而不等于执行任意代码。
2. **行为空间必须有界。** 封闭算子表，禁止用户 `registerOperator`，未知 `type` 直接挂在校验期。
3. **必须可预览、可补偿。** 同一份协议：`run` 真跑副作用，`preview` 永不调用业务函数；失败后按栈逆序 rollback。
4. **必须跨宿主搬迁。** 同一份编排在文档站、React、Node 里解释，不绑某一框架的模块图。

注意这些目标里，没有一条是「比手写 JS 好写」。

如果团队日常是人肉写长 FlowSpec，只是把 `if` 换成 JSON，ROI 就是负的。配置化在这里不是省事，是税。

## 我们试过、也打算继续砍的方向

**试过的诱惑：** 把业务能力也收成「可配置算子」，用更多 params 盖住项目差异。这正是组件库成功路径的镜像，用在逻辑上会重复 VueUse 被冷落的结局：表越长，人越不写。

**现在的切法：**

- **语法层封闭、可穷举**：控制流和纯计算进引擎词表，按版本发版，不按项目注册。
- **业务层仍是函数**：只经 `callFunc` 注入。项目差异写在 TypeScript 里，不写进算子 Catalog。
- **复杂度故意分层**：先保证 `then` / `if` / `set` / `callFunc` 能跑通结算，再谈循环、集合、并发。不把「完整 JS」当目标。

一句话：编排像语言子集，业务像手写函数。不要做成「逻辑版 Element Plus」。

## 配置化该问的三个问题

开工前先问清楚，少造一门没人用的方言：

1. **变化轴是外观，还是业务语义？** 外观近似有限配置空间；业务语义通常不是。
2. **消费者是人写长配置，还是机器生成短协议？** 后者才吃「程序即数据」的红利。
3. **你需要的是机制库，还是业务叙事框架？** 机制用 hooks；叙事用函数；只有编排契约才值得进 DSL。

如果三个问题里你都答「我想让业务同学少写代码」，结果多半是：业务同学不写，前端同学多维护一套解释器。

## 已知局限

这套判断偏前端与中等复杂度 B 端。强监管、强审计、协议必须由运营系统下发的场景，JSON 编排的溢价更高，手写 TS 反而难过审。

我们也还没证明「短编排 + 厚函数」在大型团队里一定比「纯 TS 模块」更省总成本。它省的是校验与预览，不是键盘敲击次数。

## FAQ

**Q: 那 VueUse / ahooks 还要不要用？**  
要。用在机制层：防抖、生命周期、浏览器 API。别指望它们吃掉你的领域模型。

**Q: 低代码平台是不是都在骗自己？**  
不全是。做成「表单/流程零件」且变化轴可控的，能活。做成「用配置写完整程序」的，往往悄悄长回 IDE。

**Q: 什么时候该上声明式编排 DSL？**  
当你需要协议可校验、可预览、可跨宿主解释，并且愿意把业务压回函数、把 DSL 压到语法子集。若只是想少写 `if`，别上。

**Q: 配置化有没有「正确剂量」？**  
有。视图侧可以重；逻辑侧只配置机制与编排骨架；业务语义默认手写。超过这个剂量，你就是在用 JSON 交语法税。
